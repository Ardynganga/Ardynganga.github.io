Tester la sécurité d'une API REST : par où commencer ?

Une API expose directement vos données et vos règles métier. Voici la démarche que je suis pour l'évaluer, du périmètre autorisé jusqu'au rapport.

Une application mobile ou un site moderne n'est souvent qu'une façade : tout se joue dans l'API. Si elle accepte une requête, peu importe ce que l'interface interdisait. C'est pourquoi le test d'une API est devenu le cœur d'un test d'intrusion applicatif.

Avant tout : une autorisation écrite

Tester un système sans l'accord de son propriétaire est illégal, même avec de bonnes intentions. Un test sérieux commence par un document signé qui précise :

  • les adresses et environnements concernés, de préférence une préproduction ;
  • les dates et les plages horaires des tests ;
  • les comptes de test fournis, au moins deux par rôle ;
  • ce qui est exclu : déni de service, données réelles de clients, services tiers.

Les exemples ci-dessous supposent ce cadre. Le domaine api.exemple.test est fictif.

1. Dresser l'inventaire

On ne teste bien que ce que l'on connaît. La documentation OpenAPI, quand elle existe, donne la liste des routes, des méthodes et des paramètres. Elle se complète par l'observation du trafic de l'application avec un proxy d'interception.

Cherchez aussi ce qui n'est pas documenté : anciennes versions encore servies (/v1/ alors que l'application utilise /v2/), routes d'administration, environnements de test oubliés. Les versions abandonnées gardent souvent les failles corrigées ailleurs.

2. Éprouver l'authentification

Pour une API à jetons JWT, quelques questions simples révèlent beaucoup :

  • Une route protégée répond-elle sans jeton ?
  • Un jeton expiré est-il vraiment refusé ?
  • Un jeton dont le contenu a été modifié sans nouvelle signature est-il rejeté ?
  • Le jeton reste-t-il valable après la déconnexion ?
# Sans jeton : la réponse attendue est 401
curl -s -o /dev/null -w "%{http_code}\n" https://api.exemple.test/v1/commandes/

# Avec le jeton du compte de test A
curl -s -H "Authorization: Bearer $JETON_A" https://api.exemple.test/v1/commandes/

3. Vérifier les autorisations, objet par objet

C'est le premier risque du classement OWASP API Security : l'API vérifie que vous êtes connecté, mais pas que l'objet demandé est le vôtre. Le test demande deux comptes.

# La commande 1042 appartient au compte B. On la demande avec le jeton de A.
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $JETON_A" \
  https://api.exemple.test/v1/commandes/1042/

Une réponse 200 est une faille : n'importe quel client peut lire les commandes des autres en parcourant les numéros. La réponse attendue est 404 ou 403. Le test se répète pour chaque méthode, car une lecture bien protégée cohabite parfois avec une modification ou une suppression oubliées.

Les fonctions réservées

Même principe pour les rôles : un compte client ne doit pas atteindre les routes d'administration, même en devinant leur adresse.

4. Regarder ce que l'API accepte et renvoie

Deux défauts vont souvent ensemble. Le premier : l'API renvoie plus de champs que l'écran n'en affiche (adresse, téléphone, rôle interne). Le second : elle accepte en écriture des champs que l'utilisateur ne devrait pas contrôler.

curl -s -X PATCH https://api.exemple.test/v1/profil/ \
  -H "Authorization: Bearer $JETON_A" \
  -H "Content-Type: application/json" \
  -d '{"nom": "Test", "role": "admin", "solde": 99999}'

Si le rôle ou le solde changent, le serveur fait confiance au client. La correction se fait côté serveur : une liste explicite de champs modifiables, et des montants toujours recalculés par le serveur.

5. Mesurer les limites

Une API sans limite de débit laisse deviner des mots de passe, aspirer des données ou saturer le service.

for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST https://api.exemple.test/v1/auth/login/ \
    -H "Content-Type: application/json" \
    -d '{"email": "test@exemple.test", "password": "incorrect"}'
done

Vingt réponses 401 d'affilée, sans blocage ni 429, signalent une connexion exposée aux essais en série. Ce test reste volontairement modeste : il s'agit de constater l'absence de limite, pas de mettre le service à genoux.

6. Rendre le résultat utilisable

Un test n'a de valeur que si l'équipe peut corriger. Chaque constat du rapport contient :

  • un niveau de criticité, de critique à faible ;
  • la requête exacte qui permet de reproduire le problème ;
  • l'impact concret pour l'entreprise ;
  • la correction recommandée, puis une contre-vérification une fois le correctif livré.

À retenir

La majorité des failles d'API ne demandent aucun outil sophistiqué : deux comptes, de la méthode et de la rigueur. Elles échappent pourtant aux scanners automatiques, parce qu'elles tiennent à la logique de votre métier. C'est là qu'un test manuel apporte le plus.
