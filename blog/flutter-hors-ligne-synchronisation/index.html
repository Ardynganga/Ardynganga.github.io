Flutter hors ligne : synchroniser sans perdre de données

Sur le terrain, le réseau va et vient. Une application mobile fiable enregistre d'abord sur l'appareil, puis synchronise sans créer de doublon. Voici le schéma que j'utilise.

Un agent qui encaisse une taxe sur un marché, un livreur dans un sous-sol, un infirmier dans une zone mal couverte : aucun ne peut attendre que le réseau revienne. Si l'application affiche une erreur au moment d'enregistrer, le travail est perdu, ou noté sur papier.

La réponse tient en une phrase : l'appareil est la première destination des données, le serveur la seconde. Tout le reste en découle.

Le principe : écrire en local, envoyer plus tard

Chaque action de l'utilisateur est enregistrée immédiatement dans une base locale et placée dans une file d'attente. Un processus séparé vide cette file quand le réseau est disponible. L'écran ne dépend jamais d'un appel réseau pour confirmer une saisie.

La base locale avec Drift

Drift ajoute à SQLite des requêtes typées et des migrations. La table ci-dessous sert de file d'attente.

enum StatutSync { enAttente, envoyee, rejetee }

class Operations extends Table {
  TextColumn get id => text()();                  // UUID créé sur l'appareil
  TextColumn get type => text()();
  TextColumn get donnees => text()();             // contenu JSON
  IntColumn get statut => intEnum<StatutSync>()();
  DateTimeColumn get creeLe => dateTime()();

  @override
  Set<Column> get primaryKey => {id};
}

L'identifiant naît sur l'appareil

C'est le détail qui change tout. Si le serveur attribue l'identifiant, l'application ne peut pas savoir si une opération envoyée juste avant une coupure a été reçue. Avec un UUID généré sur le téléphone, la même opération porte le même identifiant à chaque tentative.

Future<void> enregistrerPerception(Map<String, dynamic> donnees) {
  return db.into(db.operations).insert(
    OperationsCompanion.insert(
      id: const Uuid().v4(),
      type: 'perception',
      donnees: jsonEncode(donnees),
      statut: StatutSync.enAttente,
      creeLe: DateTime.now(),
    ),
  );
}

Une API qui accepte les répétitions

Côté serveur, renvoyer deux fois la même opération ne doit jamais créer deux enregistrements. C'est ce que l'on appelle une création idempotente. Avec Django, quelques lignes suffisent.

operation, creee = Operation.objects.get_or_create(
    id=request.headers["Idempotency-Key"],
    defaults={"agent": request.user, "donnees": request.data},
)
return Response(serialiser(operation), status=201 if creee else 200)

Première réception : 201. Renvoi après une coupure : 200 avec le même objet. Dans les deux cas, l'application peut marquer l'opération comme envoyée.

La boucle de synchronisation

Future<void> synchroniser() async {
  final enAttente = await (db.select(db.operations)
        ..where((o) => o.statut.equalsValue(StatutSync.enAttente))
        ..orderBy([(o) => OrderingTerm.asc(o.creeLe)]))
      .get();

  for (final op in enAttente) {
    try {
      final reponse = await http.post(
        Uri.parse('$baseUrl/api/v1/operations/'),
        headers: {
          'Authorization': 'Bearer $jeton',
          'Content-Type': 'application/json',
          'Idempotency-Key': op.id,
        },
        body: op.donnees,
      );

      if (reponse.statusCode == 200 || reponse.statusCode == 201) {
        await marquer(op.id, StatutSync.envoyee);
      } else if (reponse.statusCode >= 400 && reponse.statusCode < 500) {
        await marquer(op.id, StatutSync.rejetee);   // refus définitif
      } else {
        break;                                      // serveur indisponible
      }
    } on SocketException {
      break;                                        // plus de réseau
    }
  }
}

Trois issues, trois comportements :

  • Succès : l'opération quitte la file.
  • Refus du serveur (erreur 4xx) : réessayer ne servira à rien. L'opération est marquée et présentée à l'utilisateur avec le motif.
  • Panne ou coupure : on s'arrête et on réessaiera, dans le même ordre.

Dire la vérité à l'utilisateur

Une application hors ligne doit montrer son état : nombre d'opérations en attente, date de la dernière synchronisation, opérations refusées. Sans cela, l'utilisateur ne sait pas s'il peut éteindre son téléphone ni rendre l'appareil à un collègue.

Les pièges à éviter

  • Calculer les montants sur le téléphone. L'appareil propose, le serveur décide et recalcule.
  • Garder un jeton sans durée de vie. Un appareil perdu ne doit pas rester une porte ouverte : jetons courts, appareils autorisés un par un.
  • Synchroniser dans le désordre. Une modification envoyée avant la création qu'elle concerne échouera.
  • Oublier les données de référence. Barèmes et listes doivent être téléchargés avant le départ sur le terrain.

Ce schéma demande un peu plus de travail au départ. En échange, l'application reste utilisable partout, et aucune saisie ne dépend de la qualité du réseau.
