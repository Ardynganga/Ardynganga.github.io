Comment sécuriser une application Django ?

Django protège beaucoup de choses par défaut, mais pas tout. Voici les réglages et les réflexes qui font la différence entre une application en ligne et une application défendue.

Django a la réputation d'être un framework sûr, et elle est méritée : protection CSRF, échappement automatique dans les gabarits, requêtes paramétrées par l'ORM, hachage solide des mots de passe. Pourtant, la plupart des failles que je rencontre dans des applications Django ne viennent pas du framework. Elles viennent de la configuration de production et du code métier.

Ce guide suit l'ordre dans lequel je vérifie une application avant sa mise en ligne.

Commencer par l'audit intégré

Django fournit une commande qui relit vos réglages comme le ferait un auditeur. Elle ne prend que quelques secondes.

python manage.py check --deploy

Chaque avertissement correspond à un réglage décrit ci-dessous. L'objectif est d'arriver à zéro avertissement avec les réglages de production, pas avec ceux de développement.

Les réglages de production

Trois réglages ne se discutent pas : DEBUG désactivé, une liste d'hôtes explicite et une clé secrète qui ne figure pas dans le dépôt.

import os

DEBUG = False
ALLOWED_HOSTS = ["www.exemple.cd"]
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]   # jamais dans le code ni dans Git

Avec DEBUG = True, la moindre erreur affiche vos variables, vos chemins et une partie de votre configuration à n'importe quel visiteur.

Forcer HTTPS et protéger les cookies

SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000            # un an, à activer une fois HTTPS stable
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True

# Derrière un proxy (Nginx, Traefik…), indiquer comment reconnaître HTTPS
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")

Un cookie de session envoyé en clair sur un Wi-Fi public suffit à voler un compte. Ces lignes ferment cette porte.

Le contrôle d'accès, première source de failles

Être connecté ne veut pas dire avoir le droit. La faille la plus fréquente, et la plus simple à exploiter, consiste à changer un identifiant dans l'adresse pour lire les données d'un autre.

# Vulnérable : tout utilisateur connecté peut lire n'importe quelle facture
@login_required
def facture(request, pk):
    facture = get_object_or_404(Facture, pk=pk)
    return render(request, "facture.html", {"facture": facture})


# Corrigé : la requête elle-même est limitée au propriétaire
@login_required
def facture(request, pk):
    facture = get_object_or_404(Facture, pk=pk, client=request.user)
    return render(request, "facture.html", {"facture": facture})

La règle : le filtre d'appartenance se place dans la requête, pas dans un if ajouté après coup. Pour une API, la même logique s'applique dans get_queryset(). Une ressource qui ne vous appartient pas doit répondre comme si elle n'existait pas.

Injections : garder l'ORM de son côté

L'ORM paramètre les requêtes à votre place. Le danger revient dès que l'on assemble du SQL à la main.

# Vulnérable : la valeur est collée dans la requête
Client.objects.raw(f"SELECT * FROM clients WHERE nom = '{nom}'")

# Correct : la valeur est transmise comme paramètre
Client.objects.raw("SELECT * FROM clients WHERE nom = %s", [nom])

Même vigilance dans les gabarits : l'échappement automatique protège contre le XSS tant que vous n'utilisez pas |safe ou mark_safe() sur un contenu saisi par un utilisateur.

Ralentir les attaques sur la connexion

Sans limite, un formulaire de connexion accepte des milliers d'essais par minute. Le paquet django-axes bloque un compte ou une adresse après plusieurs échecs.

AXES_FAILURE_LIMIT = 5      # essais autorisés
AXES_COOLOFF_TIME = 1       # heure(s) de blocage

Ajoutez une longueur minimale de mot de passe dans AUTH_PASSWORD_VALIDATORS et, pour les comptes sensibles, une double authentification.

Surveiller les dépendances

Une application sûre aujourd'hui ne l'est plus le jour où une faille est publiée dans une de ses bibliothèques.

pip install pip-audit
pip-audit -r requirements.txt

Lancez cette vérification dans votre intégration continue et suivez les versions de sécurité de Django : elles sont annoncées à l'avance.

La liste à garder sous la main

  • check --deploy sans avertissement avec les réglages de production.
  • DEBUG désactivé, hôtes explicites, secrets dans l'environnement.
  • HTTPS forcé, HSTS activé, cookies marqués Secure.
  • Chaque vue filtre les données selon l'utilisateur connecté.
  • Aucun SQL assemblé avec des valeurs saisies.
  • Tentatives de connexion limitées et journalisées.
  • Dépendances auditées à chaque livraison.

Ces vérifications couvrent l'essentiel, mais elles ne remplacent pas un regard extérieur : un test d'intrusion cherche ce que la liste ne prévoit pas, en particulier les erreurs de logique propres à votre métier.
